### 1. SMTP Round-Robin Distribution Fix
**Problem**: All emails were only sending from 1 SMTP server (`email-sendgrid2`) despite having 2 servers enabled.

**Root Cause**: The `selectServer` function in `internal/queue/processor.go` always picked the server with the highest `DailyRemaining` capacity. When both servers had unlimited capacity (`DailyLimit = 0`), they both got `DailyRemaining = 999999999`, and due to Go's non-deterministic map iteration, the same server was consistently selected.

**Solution**: Implemented round-robin selection when servers have equal capacity:
- Added `rrCounter` and `rrMutex` to Processor struct
- When multiple servers have the same `DailyRemaining`, collect them all
- Sort by UUID for consistent ordering
- Use atomic counter to distribute emails in round-robin fashion

### 3. Rate Limit Auto-Disable Feature
**Request**: When Azure returns a rate limit error, automatically disable that SMTP server for the specified cooldown period (plus 10% margin), then auto-re-enable.

**Implementation**:
- Created new `internal/ratelimit/tracker.go` module
- Detects rate limit errors from:
  - SMTP send errors (patterns: "too many requests", "rate limit", "throttl", Azure codes)
  - Azure webhook delivery reports with "Failed" or "Throttled" status
- Parses Retry-After values or uses 1-hour default cooldown
- Adds 10% margin to all cooldown periods
- Disables server by updating database settings (`enabled = false`)
- Background scheduler checks every minute to re-enable expired servers

## Key Architectural Decisions

### Round-Robin Selection
- Uses mutex-protected counter for thread safety
- Servers sorted by UUID to ensure consistent ordering across restarts
- Only applies when servers have equal capacity (same DailyRemaining value)
- Logs each round-robin selection for debugging
